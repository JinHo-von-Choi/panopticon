# 실행계획 구현 결정 기록

대상 계획: 「Panopticon 개선 및 경쟁력 강화 실행계획」 19페이지

이 문서는 각 장에서 무엇을 결정했는지, 왜 그렇게 결정했는지, 어떻게
검증했는지를 기록한다. 결정의 근거가 아니라 결정의 이유를 남긴다.

---

## 1장 · 경보 근거와 오프라인 변경 비교

### 결정

| 항목 | 결정 | 이유 |
|-|-|-|
| 기록 분리 | Evidence, Trace, ReplayRun 을 별도 테이블로 분리 | 세 가지는 서로 다른 질문에 답한다. 합치면 하나가 없을 때 나머지도 쓸 수 없게 된다 |
| 비교 불가 사유 | `replay_runs.non_comparable_reasons` 를 컬럼으로 지정 | 사유 없는 비교는 만들 수 없어야 한다 |
| 지원 엔진 | arp_spoof, port_scan, data_exfil 3종 | G2·G3 를 통과한 것만 재현 범위에 넣는다 |
| 결과 형태 | 관측만. 악성 판정 없음 | 경보 감소는 오탐 감소의 증거가 아니다 |
| payload 엔진 | 원본 없으면 재현 불가 | 해시나 화면 요약으로 원본을 대신하지 않는다 |
| 실행 위치 | 운영 Dispatcher 미호출 | 격리가 깨지면 비교 결과가 운영 경로의 상태가 된다 |
| 실행 방식 | 비동기 작업 | 무거운 작업을 요청 스레드에 두면 대시보드가 멈춘다 |
| 예산 | 동시 1개, 10분, 원본 256MB | 초과 시 중단하고 사유를 남긴다 |

### 검증

- 동일 입력 반복 실행 시 결과 지문 일치
- 값이 같고 순서가 다르면 다른 지문
- 격리된 실행이 `events` 테이블에 행을 남기지 않음을 실제 DB 로 확인
- 비교 불가 사유 7종 각각에 대해 결과가 `comparable: false` 로 표시됨

## 2장 · Shadow 정책과 확인 가능한 만료 복구

### 결정

| 항목 | 결정 | 이유 |
|-|-|-|
| 상태 분리 | 승인(결정)과 적용(실행)을 분리 | "승인됐으나 적용 안 됨" 을 표현할 수 없는 상태는 성공으로 뭉개진다 |
| 승인 고정 | 대상·방향·TTL·scope 의 해시를 승인 시점에 저장 | 승인 뒤 바뀌면 다른 것으로 승인받은 셈이 된다 |
| 불일치 처리 | 409 로 거부, 재승인 요구 | 자산 매핑이 바뀌면 사람이 다시 봐야 한다 |
| 만료 | `expire_at` 은 최초 확정값 | 재시도로 늘리면 실제 노출 시간이 계획보다 길어진다 |
| 중복 | idempotency key | 재시도는 중복 적용을 만들지 않는다 |
| 확인 실패 | `unknown` | 확인하지 못한 것을 확인했다고 기록할 수 없다 |
| 백엔드 | shadow 와 nftables 2종 | OS 를 건드리지 않는 상태는 기능이 아니라 기본값이다 |
| 만료 검증 | 실측. 검증 통과 후에만 적용 허용 | 매뉴얼 인용으로 참을 만들지 않는다 |
| nftables 범위 | IPv4, input, timeout set 전용 | 이 백엔드가 표현할 수 있는 것을 넘어 표현하지 않는다 |
| 대상 보호 | 사설 대역·관리망·루프백 제외 | 모르겠으므로 건드리지 않는다 |
| 자동 차단 | 기본 꺼짐 | 백엔드가 있어도 켜려면 사람이 정해야 한다 |
| 속도 제한 | 동시 3개, 분당 1개 | 복구 불가한 상태를 만들지 않기 위한 상한 |
| 상한 차감 시점 | 실행이 실제로 나갈 때만 | 거절된 요청이 상한을 먹으면 실행 가능한 조치까지 막는다 |
| 영구 조치 | 불가 | TTL 이 없는 조치는 복구 수단이 없다 |

### 검증

- `ip filter` 테이블, 비우기 명령, 타 규칙 삭제 없음
- 생성되는 명령이 argv 배열이며 셸을 사용하지 않음
- 커널 만료를 격리 네트워크 네임스페이스에서 실측. 만료 전 존재, 만료 후 부재,
  잔여 원소 0 을 모두 확인
- 만료 후 set 은 존재하고 원소만 사라진다. 잔여 원소 수로 판단한다
- 만료 미검증 상태에서의 적용 시도가 거부됨
- 승인 불일치 5종이 모두 409 를 반환함
- 분당 1개 초과 시 429 를 반환하고, 거절된 조치는 `requested` 상태로 남음.
  연결 이전에는 같은 요청이 200 으로 통과했다
- 409 로 거절된 요청은 상한을 소모하지 않는다. 상한을 검사보다 앞에서 걸면
  거절된 요청이 실제로 실행 가능한 조치까지 막는다. 이 순서를 뒤집은
  구현에서 노예 테스트가 실패했다

### 한계

권한 분리가 이 배포 구조에서는 완전하지 않다. 실행기는 입력 범위를 좁히지만
웹 프로세스가 방화벽 권한을 얻는다. 별도 권한 프로세스로 분리해야 완결된다.

적용 속도 제한은 라우터 인스턴스 단위다. 프로세스 안에서만 유효하므로 여러
프로세스가 같은 장비를 다룬다면 총량이 제한을 넘을 수 있다.

## 3장 · 관측 범위와 누락 표시

### 결정

| 항목 | 결정 | 이유 |
|-|-|-|
| 상태 | observed / partial / stale / unknown | "관측 없음" 과 "관측 결과 없음" 은 다른 상태다 |
| heartbeat | 10초 주기, 3회 누락 시 stale | 센서 생존을 확인할 수 없을 때 경보를 근거로 쓸 수 없다 |
| 계측 지점 | capture, input_queue, engine, result_queue, db | 단계별 분모가 있어야 손실률이 성립한다 |
| 계측 비용 | 패킷 경로에서 배치 합산 | 패킷마다 잠그면 계측이 측정 대상이 된다 |
| 손실 | 앱 drop 과 커널 drop 분리 | 분모와 원인이 다르다 |
| 분모 | 같은 단계·같은 시간창의 수신 | 다른 분모를 섞으면 비교가 되지 않는다 |
| 링크 손실 | `unknown` | 측정할 수 없는 값을 만들지 않는다 |
| 트래픽 0 | 장애로 판정하지 않음 | 조용한 구간일 수 있다 |
| DB 실패 | 계측에 기록 | 경보가 없는 상태로 보이지 않게 한다 |
| 속도 제한 | 억제로 별도 집계 | 억제는 손실이 아니다 |

### 검증

- 배선 이전 구현에서 계측 테스트 10건이 모두 실패
- heartbeat 미도달 시 stale 판정
- 입력 큐 10% 이상 유실 시 partial
- 분모 0 일 때 백분율 없이 사유 반환
- 계측 지점 삭제를 심어 게이트 G0-10 이 실패함을 확인

## 4장 · 업무 영향을 고려한 최소 대응 제안

### 결정

| 항목 | 결정 | 이유 |
|-|-|-|
| 제안 구성 | 근거, 가시성 상태, 대상 매핑, match 범위, 예상 자산, 불확실성, TTL | 판단에 필요한 항목이 빠지면 되돌릴 수 없다 |
| 범위 분리 | 확정 자산과 미확인 자산을 별도 저장 | 평균 내면 판단 근거가 사라진다 |
| 좁히기 실패 | 제안 생성 자체를 거부 | 넓은 IP 차단은 위험을 옮기는 것이다 |
| 관측 게이트 | stale·unknown 이면 조치 생성 금지 | 확인되지 않은 관측에 근거한 조치는 근거가 없다 |
| 매핑 | 오래되면 제안엔 불확실성, 실행은 거부 | 제안은 사람이 읽고 실행은 목적이 있다 |
| 제안 생성 | 규칙 기반만 허용 | AI 는 scope 와 TTL 을 결정하지 않는다 |
| 출력 | `approved: false` 명시 | 201 응답이 적용 성공으로 읽히면 안 된다 |

### 검증

- 공유 IP, 오래된 매핑, 미확인 매핑에서 사유가 기록됨
- IP 단위만 가능한 범위에서 409
- 관측 stale·unknown 에서 409
- AI 출처 403

## 지원 모드

| 프로필 | 범위 |
|-|-|
| limited | 관측, 탐지, 대시보드, 승인 큐. 강제 적용 없음 |
| general | limited + shadow 정책 |
| extended | general + 검증된 강제 백엔드 |

프로필 선택과 조합 검사는 분리되어 있다. 어떤 조합이 지원되는지와 지금
무엇이 검증되었는지는 다른 질문이다.

## 검증 방법

| 층위 | 방법 |
|-|-|
| 게이트 | `python scripts/gates.py` |
| 단위 | 경계값과 실패 경로 |
| 통합 | 실제 PostgreSQL, 실제 엔진, 실제 디스패처 |
| 노예 | 실제 경로 종단간. 모킹 없음 |
| 커널 | 격리 네트워크 네임스페이스에서 nftables 만료 실측 |

실제 DB 를 쓰는 라우터 테스트는 같은 이벤트 루프의 `httpx.ASGITransport` 를
사용한다. `TestClient` 은 앱을 별도 루프에서 실행하므로 asyncpg 커넥션이
끊긴다.
