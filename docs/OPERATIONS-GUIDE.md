# 운영 가이드

이 문서는 설치된 Panopticon의 상태 확인, 백업, 저장 장애와 증거 보존을 다룹니다. 설치는 [설치 가이드](INSTALL.md), 사건 조사는 [사용 가이드](USER-GUIDE.md)를 참고하세요.

## 상태 확인

대시보드의 관측 상태와 저장·알림 상태를 함께 확인합니다. 경보가 없더라도 관측이나 저장이 중단됐을 수 있습니다.

| 주소 | 확인하는 내용 |
| --- | --- |
| `/health` | 프로세스의 HTTP 응답 |
| `/ready` | DB·센서 등 주요 구성요소의 준비 상태. 준비되지 않았으면 HTTP 503 |
| `/api/health` | 인증 후 확인하는 구성요소별 상태와 실패 원인 |
| `/api/observation` | 관측 구간, 단계별 계수와 누락 정보 |
| `/api/support-profile` | 현재 설정의 지원 범위와 구성 오류 |
| `/metrics` | 수집 가능한 운영 지표 |

```bash
curl --fail http://127.0.0.1:38585/ready
docker compose logs --tail=100 netwatcher
```

HTTPS 또는 다른 포트로 운영한다면 주소를 바꾸세요. 인증이 필요한 API와 지표는 [API 가이드](API.md)의 Bearer 토큰을 사용합니다.

## 백업

업데이트와 중요한 설정 변경 전에 다음을 보관합니다.

- PostgreSQL DB
- 사용하는 설정 디렉터리와 별도로 보호한 `.env`
- 조사 중인 패킷 증거와 `review-pins.json`
- 복구 기능을 켰다면 `data/recovery`의 미확정 사건 파일

Compose에 포함된 DB의 백업 예시입니다. 파일에는 사건과 장치 정보가 들어 있으므로 접근 권한을 제한합니다.

```bash
umask 077
docker compose --profile db exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > panopticon-backup.dump
```

DB와 설정, 증거 파일을 같은 백업 시점에 묶어 기록합니다. 복구 전에는 앱을 멈추고 기존 자료를 별도로 보관한 뒤, 해당 버전에 맞는 스키마와 설정을 복원합니다. 실제 서비스 DB가 아닌 별도 DB에서 복원 시험을 먼저 수행하세요.

## DB 장애와 복구

DB가 끊기면 저장 재시도가 진행됩니다. 메모리 대기열과 보존 시간에는 상한이 있으므로 장시간 장애에서 모든 사건을 보존할 수는 없습니다.

선택형 복구 파일 기능을 켜면 저장이 확인되지 않은 사건 배치를 디스크에 남깁니다. DB가 돌아오거나 앱이 재시작되면 같은 사건 식별자로 복구합니다. DB의 저장 응답만 유실된 경우에도 중복 행을 만들지 않습니다. 외부 알림과 방화벽 조치는 재실행하지 않습니다.

1. DB 연결과 디스크 여유를 확인합니다.
2. `/api/health`의 `components.alert_queue.recovery_spool`에서 대기·거부·만료 수를 확인합니다.
3. DB 연결이 복원된 뒤 대기 파일이 줄고 새 사건이 저장되는지 확인합니다.
4. 손상 파일이 있으면 앱을 멈추고 해당 디렉터리를 보관합니다. 원본을 삭제하거나 빈 파일로 대체하지 마세요.
5. 파일의 형식·사건 식별자·크기·만료 정보를 점검한 뒤 복구합니다.

복구 기능은 기본적으로 꺼져 있으며, [설정 가이드](CONFIGURATION.md#db-장애-복구-파일)에서 켤 수 있습니다. 전원 장애와 파일 쓰기 실패에서 무손실을 보장하지는 않습니다.

## 패킷 증거 보존

사건 상세의 저장 이력과 현재 파일 가용 상태를 함께 봅니다. 증거는 패킷 버퍼와 수집 정책에 따라 일부만 남을 수 있습니다.

관리자가 조사 사유를 입력하면 해당 파일을 최대 24시간 보존할 수 있습니다. 전체 보존 상한은 64파일·32 MiB입니다. 상한을 넘으면 새 보존 요청이 거부됩니다. 보호된 파일로 저장 공간이 가득 찼다면 새 증거 기록이 실패할 수 있습니다.

보존 상태는 `review-pins.json`에 기록돼 재시작 후에도 유지됩니다. 이 파일이 손상되면 증거 정리와 새 기록을 중단합니다. 원본을 보관하고 조사 중인 파일과 만료 시각을 대조해 복구하세요.

보존을 일찍 해제하려면 관리자 권한으로 다음 API를 호출합니다.

```http
POST /api/events/{event_id}/evidence/pin
Authorization: Bearer <token>
Content-Type: application/json

{"enabled": false, "reason": "조사가 끝나 일반 보존 정책으로 전환"}
```

사건 조회 권한으로 `GET /api/events/{event_id}/evidence/file`에서 현재 파일을 내려받을 수 있습니다. 패킷 파일은 민감한 자료가 될 수 있으므로 접근 계정과 반출 범위를 제한합니다.

## 설정 변경과 실패

대시보드 설정 저장에는 쓰기 가능한 설정 디렉터리가 필요합니다. 읽기 전용 Docker 배포에서는 변경 요청이 실패합니다. HTTP 200이라도 승인 결과의 `applied=false`와 오류가 있다면 적용되지 않은 것입니다.

제안 생성 이후 설정이 바뀌면 이전 후보를 승인하지 말고 현재 설정을 기준으로 다시 제안·비교합니다. 적용 후에는 실제 설정값과 탐지 상태를 확인합니다. AI는 후보를 제안하며 관리자가 승인합니다.

## 알림과 관측 장애

| 증상 | 처리 |
| --- | --- |
| 장치나 통신이 보이지 않음 | 인터페이스·SPAN 범위·BPF·실제 통신 발생 여부 확인 |
| 대기열이 계속 증가 | DB 지연·입력 부하·디스크 지연을 확인하고 수집 범위 조정 |
| 관측 누락 표시 | 같은 단계·같은 시간의 수신 수와 누락 수를 확인 |
| 알림 비활성 | 사용할 채널의 접속 정보와 활성화 설정 확인 |
| 알림 실패·미확정 | 원격 채널의 수신 결과 확인. 중복 전송 가능성을 검토한 뒤 재전송 |
| 패킷 저장 실패 | 디스크 용량·파일 상한·권한·보존 파일·저장 대기열 확인 |

앱에서 누락된 패킷과 커널·네트워크 장비의 누락은 분리해서 봅니다. 측정할 수 없는 구간은 비율로 환산하지 않습니다. 요청한 입력량과 실제 센서에 도착한 입력량도 구분해야 합니다.

## 종료와 재시작

```bash
docker compose stop netwatcher
docker compose up -d netwatcher
```

호스트 서비스는 `sudo systemctl stop netwatcher`, `sudo systemctl start netwatcher`를 사용합니다. 중지할 때는 로그의 미저장·미확정 작업을 확인하고 재시작 후 준비 상태와 복구 대기를 확인합니다.

앱은 유한한 종료 시간을 사용합니다. 디스크나 커널 작업이 멈춘 경우에는 종료 시간 안에 저장을 확정하지 못할 수 있습니다. 강제 종료 후에는 DB와 증거·복구 파일의 상태를 다시 확인하세요.
