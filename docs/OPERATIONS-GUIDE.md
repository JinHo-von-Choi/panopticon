# 운영 가이드

이 문서는 설치된 Panopticon의 상태 확인, 백업, 저장 장애와 증거 보존을 다룹니다. 설치 절차는 [설치 가이드](INSTALL.md)를 참고하시고, 사건 조사는 [사용 가이드](USER-GUIDE.md)를 확인하시기 바랍니다.

## 상태 확인

대시보드에서는 관측 상태와 더불어 저장 및 알림 상태를 함께 점검합니다. 화면에 경보가 따로 뜨지 않더라도 실제 관측이나 저장 작업이 중단되었을 수 있습니다.

| 주소 | 확인하는 내용 |
| --- | --- |
| `/health` | 프로세스의 HTTP 응답 |
| `/ready` | DB·센서 등 주요 구성요소의 준비 상태. 준비되지 않았으면 HTTP 503 |
| `/api/health` | 인증 후 확인하는 구성요소별 상태와 실패 원인 |
| `/api/observation` | 관측 구간, 단계별 계수와 누락 정보 |
| `/api/support-profile` | 현재 설정의 지원 범위와 구성 오류 |
| `/metrics` | 수집 가능한 운영 지표 |

```bash
curl --fail http://127.0.0.1:38585/ready
docker compose logs --tail=100 netwatcher
```

HTTPS 환경이거나 기본과 다른 포트로 운영한다면 주소를 알맞게 변경하십시오. 인증을 요구하는 API와 지표 확인에는 [API 가이드](API.md)에 안내된 Bearer 토큰을 사용합니다.

**운영 상태 → 위협 피드** 화면으로 이동해 갱신 상태와 마지막 성공 시점으로부터 흐른 시간을 점검합니다. 만약 **확인 불가** 상태가 표시된다면 센서 연결 상태를 먼저 확인한 뒤 다시 조회하십시오. 지표 수 항목이 `—`로 나타나는 것은 수량을 정상적으로 가져오지 못했다는 뜻이지 결코 0개를 의미하지는 않습니다.

피드별 목록에서는 성공 시각과 최근 다운로드·캐시·실패 결과가 함께 표시됩니다. **일부 피드 확인 필요** 문구가 보이면 지연이 발생했거나 성공 시각 확인이 불가능한 피드부터 우선 점검하십시오. 전체 갱신 시각이 최근으로 나오더라도 다른 개별 피드들까지 모두 최신 상태라고 단정할 수는 없습니다. 재시작을 거친 후 원본 서버로부터 직접 검증받지 못한 캐시 데이터에는 이전 성공 시각을 임의로 추정해 표기하지 않습니다.

다운로드 작업이 실패하여 캐시 데이터를 읽어왔을 때는 마지막 성공 시각이 갱신되지 않고 그대로 유지됩니다. 원본 다운로드가 성공을 거두거나 원본 서버가 조건부 요청을 통해 캐시의 유효성을 최종 확인해 주어야 비로소 성공 시각이 바뀝니다. 캐시를 활용해 당장 탐지를 이어갈 수는 있겠으나, 피드 내용이 오래된 상태라면 다운로드가 실패한 원인을 추적해 바로잡으셔야 합니다.

## 분리 센서의 설정 제안

독립 센서와 콘솔을 분리해 운영하는 환경이라면 **운영 상태 → 설정 제안 승인** 메뉴에서 포트 스캔 임계값을 변경할 수 있습니다. 단순 제안 제출이나 검증 결과 연결 단계에서는 운영 설정이 즉각 바뀌지 않습니다. 분석 담당자가 제안과 검증 작업을 수행하며, 최종적으로 관리자가 승인 절차를 마쳐야 실제 운영에 반영됩니다. 조회 권한 사용자는 목록을 열람하는 것만 허용됩니다.

1. 현재 임계값을 확인하고 제안 임계값과 이유를 입력한 뒤 **제안 제출**을 누릅니다.
2. 제안의 **검증**을 눌러 정상·공격 특징값 JSON 파일을 각각 올립니다. 입력의 레이블과 변경 전후 값을 확인하고 **정상·공격 입력 비교**를 실행합니다. 파일 형식과 비교 범위는 [사용 가이드](USER-GUIDE.md)를 참고하세요.
3. 비교 결과가 조건을 충족하면 **제안에 검증 결과 연결**을 누릅니다. 관리자는 연결된 근거를 검토한 뒤 **승인**하거나 **거절**합니다.

현재 설정이 이미 변경되었다는 안내 메시지가 표시되면 새 설정을 확인한 다음 제안을 처음부터 다시 진행하십시오. 센서를 재시작하기 전에 제출해 두었던 제안 건에도 동일한 원칙이 적용됩니다. 처리 결과를 즉시 확인할 수 없는 상황이라 해서 동일한 변경 작업을 반복 실행하지 마시고, **상태 다시 확인** 버튼을 눌러 목록과 반영 상태부터 차분히 확인하시기 바랍니다.

## AI 분석 상태와 기록

**AI 분석기** 메뉴에서는 분석 도구와 실행 상태, 분석 주기 및 관련 기록을 확인합니다. 화면의 **정지** 표시는 서비스 설정은 존재하나 분석 작업 자체가 실행되지 않는 상태를 의미합니다. 반면 **사용 안 함**은 센서 장비 내에 AI 분석 서비스가 아예 구성되어 있지 않음을 뜻합니다. **상태 확인 불가**가 뜨면 센서 연결 상태를 점검하신 후 **새로고침**을 누르십시오.

판정 필터를 활용해 위협이나 오탐 의심 항목, 혹은 설정 제안을 검색하여 조사 근거를 확인합니다. AI의 판정은 어디까지나 참고용 자료일 뿐이며, 설정 제안은 철저한 검증과 관리자의 승인을 거쳐야만 시스템에 적용됩니다. 기록 조회가 실패했을 때는 화면에 출력된 오류 안내 문구를 살핀 후 다시 조회하시기 바랍니다.

## 백업

소프트웨어 업데이트나 중요한 환경 설정을 변경하기 전에는 아래 항목들을 반드시 따로 백업해 둡니다.

- PostgreSQL DB
- 사용하는 설정 디렉터리와 별도로 보호한 `.env`
- EVE 모드: 조사에 필요한 원본 Suricata 로그
- 직접 캡처 모드: 패킷 증거와 `review-pins.json`
- 복구 기능을 켰다면 `data/recovery`의 미확정 사건 파일

Compose 환경에 포함된 DB 백업 명령 예시입니다. 설치 도구가 자동 생성한 `installation/.env` 파일을 그대로 활용합니다. 기존 환경에 수동 설치한 경우라면 해당 환경의 설정 파일 경로를 지정해 주십시오. 백업 파일 내부에는 민감한 보안 사건 및 장치 정보가 고스란히 포함되어 있으므로 파일 접근 권한을 철저히 통제하셔야 합니다.

```bash
umask 077
docker compose --env-file installation/.env --profile db exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > panopticon-backup.dump
```

DB와 설정, 패킷 증거 파일은 동일한 시점에 함께 묶어서 관리합니다. 복원 작업 전에는 애플리케이션 프로세스를 안전하게 종료하고 기존 데이터를 백업한 뒤, 해당 엔진 버전에 알맞은 스키마와 설정값을 복원해야 합니다. 운영 중인 실제 서비스 DB에 곧바로 적용하지 마시고, 격리된 별도 DB 환경에서 복원 테스트를 먼저 거치시기 바랍니다.

### 별도 DB에서 복원 확인하기

아래 명령은 임시 DB를 새로 생성하여 복원 과정을 검증합니다. 운영 중인 서비스 DB에는 전혀 영향을 주지 않습니다. 백업 덤프를 생성했을 때와 동일한 버전의 PostgreSQL 컨테이너 도구를 사용합니다.

```bash
export PANOPTICON_RESTORE_DB="panopticon_restore_$(date +%Y%m%d%H%M%S)_$$"
docker compose --env-file installation/.env --profile db exec -T \
  -e PANOPTICON_RESTORE_DB db sh -ceu '
    createdb -U "$POSTGRES_USER" "$PANOPTICON_RESTORE_DB"
    pg_restore -U "$POSTGRES_USER" -d "$PANOPTICON_RESTORE_DB" \
      --exit-on-error --single-transaction --no-owner --no-acl
  ' < panopticon-backup.dump
```

복원된 임시 DB의 사건 내역과 장치 업무 정보, 증거 참조 링크 및 감사 기록을 백업 당시 자료와 대조합니다. DB 복원 작업만으로는 분리 보관된 원본 EVE 로그나 원시 패킷 파일까지 복원되지는 않습니다. 함께 보관했던 보조 파일과 환경 설정도 빠짐없이 대조해 보십시오.

업데이트 유효성 검증은 복원된 DB에 새 버전 마이그레이션을 시험 적용한 후 수행합니다. 실제 서비스 DB에 마이그레이션을 적용하기 전에 사건 조회 기능과 장치 정보, 기존 감사 이력이 온전히 보존되는지 검증합니다. 이 과정에서 오류가 발생하면 서비스 DB 업데이트 작업을 즉시 중단하십시오.

시스템을 이전 버전으로 롤백할 때는 업데이트 직전 백업과 당시 버전의 설정 파일 및 증거 데이터를 세트로 묶어 사용합니다. 새 버전을 가동하는 동안 추가된 데이터는 업데이트 전 백업본에 누락되어 있으므로 별도 보관 절차를 거쳐야 합니다. 단순 애플리케이션 버전 다운그레이드나 DB 스키마 롤백 명령만 실행하는 방식으로 백업 복원 절차를 대체해서는 안 됩니다.

### 보관된 변경 요청 확인

처리가 완료된 센서 변경 요청은 감사 로그를 온전히 보존한 상태로 정리합니다. 한 번 보관 처리된 요청 ID는 재실행할 수 없습니다. 이미 완료된 요청을 재사용하려다 거부된 경우에는 감사 기록의 처리 결과와 현재 센서 설정을 먼저 대조하십시오. 추가 변경이 필요하다면 현재 설정을 기반으로 신규 요청을 생성해야 합니다.

과거 실행 도중 남겨진 미확정 요청 건 역시 실제 적용 여부가 확실히 밝혀지기 전까지는 적용 완료 상태로 임의 변경하지 않습니다. 감사 조회 결과가 **미확정**으로 남아 있다면 설정값과 증거 데이터를 면밀히 대조한 후 후속 조치를 결정하십시오. 재시도 실패 기록이 발생하더라도 센서가 최종 확정했던 원래 적용 결과는 안전하게 유지됩니다.

## DB 장애와 복구

DB 연결이 끊어지면 시스템 내부에서 저장 재시도 작업이 수행됩니다. 메모리 버퍼 대기열과 데이터 보존 시간에 기술적 상한이 존재하므로 장시간 장애가 지속되면 모든 사건 데이터를 유실 없이 보존하기는 어렵습니다.

선택형 복구 파일 기능을 활성화하면 디스크 상에 저장이 완료되지 않은 사건 배치를 안전하게 기록해 둡니다. 추후 DB 연결이 복구되거나 애플리케이션이 다시 시작되면 동일한 사건 식별자를 활용해 복원 절차를 밟습니다. DB 측의 저장 응답 패킷만 유실된 특수한 상황이 발생하더라도 중복 행은 생성되지 않습니다. 외부 시스템 알림 발송이나 방화벽 차단 연동 조치는 불필요하게 재실행하지 않습니다.

1. DB 연결과 디스크 여유를 확인합니다.
2. `/api/health`의 `components.alert_queue.recovery_spool`에서 대기·거부·만료 수를 확인합니다.
3. DB 연결이 복원된 뒤 대기 파일이 줄고 새 사건이 저장되는지 확인합니다.
4. 손상 파일이 있으면 앱을 멈추고 해당 디렉터리를 보관합니다. 원본을 삭제하거나 빈 파일로 대체하지 마세요.
5. 파일의 형식·사건 식별자·크기·만료 정보를 점검한 뒤 복구합니다.

복구 파일 기능은 기본값으로 비활성화되어 있으며, 필요 시 [설정 가이드](CONFIGURATION.md#db-장애-복구-파일)를 참조하여 활성화할 수 있습니다. 전원 공급 중단이나 디스크 파일 쓰기 실패 상황에서 완벽한 데이터 무손실을 보장하지는 않습니다.

## 패킷 증거 보존

사건 상세 화면의 저장 이력과 현재 디스크의 파일 가용 상태를 함께 점검합니다. 원시 증거 데이터는 링 버퍼 크기와 패킷 수집 정책에 따라 일부만 잔존할 수 있습니다.

관리자가 정당한 조사 사유를 입력하면 해당 증거 파일을 최대 24시간 동안 보존할 수 있습니다. 시스템 전체 보존 상한은 64파일·32 MiB입니다. 한계치를 초과할 경우 신규 보존 요청은 자동으로 거절됩니다. 만약 보존 지정된 파일들로 인해 저장 파티션이 가득 차게 되면 새로운 증거 패킷 기록 작업이 실패할 위험이 있습니다.

파일 보존 상태는 `review-pins.json` 메타데이터에 기록되어 데몬 재시작 후에도 상태를 유지합니다. 이 메타데이터 파일이 손상되면 시스템은 증거 자동 정리와 신규 기록 작업을 모두 중단합니다. 원본 파일을 안전한 곳에 복사해 둔 뒤, 조사 중이던 실제 파일과 만료 시각을 일일이 대조하여 수동 복구를 진행하십시오.

보존 지정을 조기에 해제하고자 할 때는 관리자 권한으로 아래 API를 호출합니다.

```http
POST /api/events/{event_id}/evidence/pin
Authorization: Bearer <token>
Content-Type: application/json

{"enabled": false, "reason": "조사가 끝나 일반 보존 정책으로 전환"}
```

사건 열람 권한이 부여된 사용자는 `GET /api/events/{event_id}/evidence/file` 경로를 통해 증거 파일을 직접 내려받을 수 있습니다. 패킷 덤프는 민감한 보안 정보를 담고 있을 수 있으므로 접근 가능 계정과 외부 반출 범위를 엄격히 통제하십시오.

## 설정 변경과 실패

대시보드에서 시스템 설정을 저장하려면 쓰기 권한이 부여된 설정 디렉터리가 필수적입니다. 읽기 전용 볼륨으로 구동되는 Docker 환경에서는 설정 변경 요청이 실패합니다. HTTP 200 성공 코드를 반환받았더라도 응답 페이로드 내에 `applied=false` 플래그와 오류 메시지가 포함되어 있다면 설정이 적용되지 않은 상태입니다.

제안을 작성한 이후에 기반 설정이 먼저 변경되었다면 과거의 후보 제안을 승인하지 말고 현재 설정값을 기준으로 다시 제안과 검증을 수행하십시오. 설정이 적용된 후에는 시스템에 반영된 실제 파라미터와 탐지 동작 상태를 확인합니다. AI 분석기는 후보 값을 제안할 뿐이며 최종 반영 승인은 전적으로 관리자가 담당합니다.

## 알림과 관측 장애

| 증상 | 처리 |
| --- | --- |
| 장치나 통신이 보이지 않음 | 인터페이스·SPAN 범위·BPF·실제 통신 발생 여부 확인 |
| 대기열이 계속 증가 | DB 지연·입력 부하·디스크 지연을 확인하고 수집 범위 조정 |
| 관측 누락 표시 | 같은 단계·같은 시간의 수신 수와 누락 수를 확인 |
| 알림 비활성 | 사용할 채널의 접속 정보와 활성화 설정 확인 |
| 알림 실패·미확정 | 원격 채널의 수신 결과 확인. 중복 전송 가능성을 검토한 뒤 재전송 |
| 패킷 저장 실패 | 디스크 용량·파일 상한·권한·보존 파일·저장 대기열 확인 |

애플리케이션 계층에서 누락된 패킷과 호스트 커널 또는 네트워크 물리 스위치에서 발생한 누락은 명확히 분리하여 해석해야 합니다. 직접 측정이 불가능한 불투명 구간의 손실을 임의의 비율로 환산해 추정하지 않습니다. 시스템에 수집을 요청한 트래픽 입력량과 센서 NIC에 실제 도달한 입력량 역시 엄밀히 구분하여 분석해야 합니다.

## 종료와 재시작

```bash
docker compose stop netwatcher
docker compose up -d netwatcher
```

기본 제공되는 EVE 호스트 서비스 환경에서는 `sudo systemctl stop panopticon-eve` 및 `sudo systemctl start panopticon-eve` 명령을 이용합니다. 프로세스를 내릴 때는 시스템 로그를 살펴 미저장 작업이나 미확정 트랜잭션이 남아 있는지 확인하고, 재기동 후에는 `/ready` 준비 상태와 복구 큐 상태를 점검합니다.

애플리케이션은 종료 시 유한한 타임아웃 제한 시간을 둡니다. 디스크 I/O 병목이나 커널 인터럽트로 작업이 지연되는 경우 지정된 종료 시간 내에 저장을 완전히 마무리 짓지 못할 수 있습니다. 프로세스가 강제 종료된 후에는 DB 무결성과 패킷 증거 및 복구 스풀 파일의 온전성을 다시 점검하십시오.

### 분리 센서 재시작

`install_native.py` 스크립트로 설치한 직접 캡처 환경에서는 콘솔 컨테이너와 센서 프로세스를 반드시 한 쌍으로 묶어 중지 및 기동해야 합니다. DB, 설정, 증거 데이터가 보관된 Docker 볼륨은 임의로 삭제하지 않습니다.

```bash
docker compose --env-file installation-native/.env -f docker-compose.yml -f docker-compose.native.yml --profile db stop netwatcher native-sensor
docker compose --env-file installation-native/.env -f docker-compose.yml -f docker-compose.native.yml --profile db up -d netwatcher native-sensor
```

센서 데몬이 비정상 종료되면 Docker Compose 오케스트레이터가 프로세스를 자동으로 재시작합니다. 이전 세션의 DB 세션 락 소유권이 완전히 만료되기 전까지는 네트워크 재연결이 지연될 수 있습니다. 대시보드 관측 상태와 엔진 설정, 마지막 설정 변경의 감사 로그를 종합 점검한 뒤 다음 작업을 진행하십시오. 처리 결과를 명확히 확인하지 못한 변경 명령은 절대로 반복 실행해서는 안 됩니다.

시스템 재기동 시에는 이전 센서 인스턴스가 생성한 것으로 명확히 검증된 소켓 파일에 한해서만 정리를 수행합니다. 여전히 실행 중인 서버 프로세스나 소유권을 검증할 수 없는 파일은 안전하게 보존하며 서비스 기동을 중단합니다. IPC 소켓 관련 오류가 지속적으로 발생하는 경우 현재 동작 중인 센서 PID, 소켓 경로, 파일 퍼미션 소유권을 면밀히 확인하십시오. 소켓 디렉터리와 소유권 기록 파일을 일괄 삭제하는 방식은 삼가야 합니다.
