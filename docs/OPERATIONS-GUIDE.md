# 운영 안내

## 1. 이 도구의 정체

트래픽을 수집하고 탐지 규칙으로 경보를 만들고, 경보를 PostgreSQL과 대시보드에
보여주는 도구다. 경보 기록을 근거와 함께 남기며, 설정 변경은 사람이 승인해야
적용된다.

대시보드는 기본적으로 `127.0.0.1:38585` 에서만 접속된다.

### 상태 확인과 요청 보호

`GET /health`는 HTTP 프로세스의 생존만 확인하며 센서 정상 여부를 보장하지 않는다.
`GET /ready`는 DB 연결·실행 중인 센서·활성 엔진·유한 경보 큐·관측 창을 확인한다.
모두 정상일 때 200, 미연결·과부하·stale·unknown 상태에서는 503을 반환한다.
상세 이유는 인증된 `GET /api/health`에서 확인한다. WebSocket 연결과 준비 상태는 별개다.

로그인은 직접 연결 IP당 기본 10회/분으로 제한한다. 프록시 전달 IP 헤더로 한도를
초기화할 수 없다. 일반 API는 검증된 JWT 사용자당 기본 60회/분 + 버스트 10회이며,
토큰을 재발급해도 같은 한도를 공유한다. 현재 실행 경로의 제한은 프로세스별 로컬
버킷이고 최대 10,000개 키로 제한한다. 여러 웹 프로세스 간 공유 한도는 아직 연결하지
않았다. 거절 응답은 429와 `Retry-After: 60`을 반환한다.

변경과 접근 거절은 기존 `audit_log` 테이블에 기록한다. 요청 본문·비밀번호·토큰은
감사 기록에 넣지 않는다. 승인·적용은 먼저 승인 시도 감사가 저장돼야 실행되며,
테이블 미생성·DB 장애·2초 시간 초과 시 503으로 거부한다. `alembic upgrade head`로
기존 감사 스키마를 준비한다. 완료 응답에 대한 일반 감사 실패는 응답을 취소하지 않는다.

PostgreSQL `ssl_mode`는 실제 asyncpg 연결에 적용된다. 로컬 `disable`은 명시적 평문,
`require`는 암호화 필수, `verify-ca`는 CA 검증, `verify-full`은 CA와 호스트명 검증이다.
`postgresql.ssl_ca_file`에 CA PEM 경로를 지정하고 빈 값이면 시스템 신뢰 저장소를
사용한다. 엄격한 모드의 인증서 오류나 TLS 미지원은 평문으로 재접속하지 않는다.
`allow`·`prefer`는 평문을 허용하므로 원격 DB에서는 엄격한 모드를 선택한다.

### 경보 폭풍 시 저장 예산

`alerts.event_budget`의 기본 저장 예산은 일반 경보 120건/분, 고위험 예약
30건/분이다. 일반 경보는 예약 몫을 소비하지 않는다. 전체 예산을 초과한 경보는
`global_budget` 억제 사유와 관측 카운터에 기록하며 DB·PCAP·웹훅으로 전달하지 않는다.
키별 제한도 그대로 적용한다. 키가 10,000개에 도달하면 활성 키를 지워 한도를
초기화하지 않고 신규 키를 거부한다.

반복 집계는 기본 60초 창을 사용한다. 최초 대표 이벤트는 즉시 저장하며 반복의
count·최초/최근 시각은 만료 창당 배치 갱신한다. 심각도 상승·공격 단계·대상·정책
변경은 별도 대표로 남는다. 대표의 근거가 모든 반복 경보의 개별 원자료를 의미하지는
않는다. DB 장애 중 집계 대기량은 `/api/health`의 큐 상태에서 확인한다.

### 종료 예산

SIGTERM은 신규 캡처 입력을 거부한다. 종료 단계는 `shutdown.timeout_seconds`
(기본 10초)의 monotonic 예산을 공유하고 캡처/워커의 join은 이벤트 루프 밖에서
수행한다. 워커 join 중에도 결과 큐를 소비한 뒤 경보 저장을 배출한다. 통계는
마지막 스냅샷 저장을 시도한다. 단계별 시한 초과·통계 확인 상태·대기 경보·증거
byte를 로그에 남긴다. 미확인 작업을 저장 완료로 해석하지 않는다.

취소는 실행 중인 파일 쓰기 스레드나 커널 D-state를 강제로 중지하지 못한다.
Python executor 정리가 프로세스 퇴장을 늦출 수도 있다. 저장소의 systemd 유닛은
`TimeoutStopSec=15`, Compose 앱은 `stop_grace_period: 15s`로 마지막 프로세스
정리 경계를 둔다. 공유 호스트의 실제 서비스 설정은 자동 변경하지 않았다.
전체 운영 앱의 5초 종료 목표와 장시간 HDD/불응답 채널 부하는 아직 미검증이다.

### 알림 채널 설정

기동 시 enabled 채널의 URL 또는 Telegram 토큰·대상을 확인한다. 누락·차단된
목적지·잘못된 심각도 설정은 채널을 제외하고 채널당 한 번 경고한다. 경보와
일일 보고는 동일한 검증 목록을 사용한다. 상세 상태 API의
`components.notifications.channels`에서 `disabled_reason`을 확인한다. 선택 채널의
설정 누락은 센서 준비 상태를 실패로 만들지는 않는다. 로그에는 웹훅 URL·토큰·
원격 응답 본문을 남기지 않는다.

### 통계 저장 실패와 재시도

배포 전에 `alembic upgrade head`로 `015_flush_receipts`까지 적용한다. 통계와
디바이스 스냅샷의 UUID 확인 기록을 데이터와 원자적으로 저장한다. commit 후
응답이 끊겨도 같은 ID로 재시도하며 packet·byte를 중복 가산하지 않는다.
저장 실패는 `/api/health`의 `stats_flush`에 대기량·age와 degraded로 표시한다.

`storage.max_pending_age_seconds`는 기본 300초(최대 24시간)다. 기한이 지난
스냅샷은 미확인 packet 수를 통계/디바이스 단계별로 남긴다. 두 수는 같은 입력을
포함할 수 있으므로 합산하지 않는다. 장애 중 새 입력은 이후 스냅샷에 합쳐져
시간 구간의 정밀도가 낮아질 수 있다. 메모리 대기는 프로세스 재시작 시 복구되지
않는다. 확인 기록은 기존 유지보수 경로에서 7일이 지난 뒤 정리한다.

### PCAP 증거 저장

PCAP은 발생 전 문맥만 수집하며, 파일 I/O를 백그라운드 큐로 분리한다. 기본 패킷
링은 1,000개/8MiB, 증거 큐는 대기 32건/진행 중 포함 8MiB다. 같은 자산·유형의
반복 수집에는 60초 쿨다운이 있다. 고위험/명시 수집에는 큐의 예약 몫과 우선순위를
둔다. 한 자산은 링의 건수·바이트 몫을 제한받는다.

`metadata.pcap`의 pending/persisted/omitted/failed/volatile과 이유를 확인한다.
persisted에만 실제 파일 경로와 SHA256을 기록한다. 취소한 파일 쓰기는 계속 실행될
수 있으므로 shutdown_unconfirmed를 완료로 해석하지 않는다. 상태 갱신 DB 실패는
pending으로 남을 수 있다. 기본 저장 상한은 500MiB/10,000파일, 삭제는 최대 4개/초다.
기동 당시 파일 수가 상한을 넘으면 재고 메모리를 제한하고 새 기록을 거부한다.
승인 검토 파일의 pin 보존과 tmpfs 정책은 아직 지원하지 않는다.

## 2. 하지 않는 것

| 하지 않는 것 | 이유 |
|-|-|
| 방화벽을 변경하지 않는다 | 적용 경로가 검증되기 전이다. `response.enabled` 는 꺼져 있다 |
| 경보가 없다고 안전하다고 말하지 않는다 | 관측 범위 화면에서 센서 상태를 함께 표시한다 |
| 자동으로 접근을 막지 않는다 | 차단 정책은 제안이며, 승인 없이는 실행되지 않는다 |
| 탐지 결과의 악성 여부를 확정하지 않는다 | 관측 사실만 기록한다 |
| AI 가 승인을 하지 않는다 | AI 는 설정 제안만 올린다 |

## 3. 시작 전 확인

### 3.1 인증

기본값은 `auth.enabled: false` 이다. LAN 이상에서 대시보드에 노출하려면
아래 세 가지를 모두 설정한다.

```bash
# .env
NETWATCHER_LOGIN_ENABLED=true
NETWATCHER_LOGIN_PASSWORD=<비밀번호>
NETWATCHER_JWT_SECRET=<32바이트 이상 임의 문자열>
```

`config/default.yaml` 의 `web.host` 를 `0.0.0.0` 으로 바꾸고 인증을 켜지
않으면, 기동 전에 거부된다. 지원 계약 SUP-020 의 조건이다.

`NETWATCHER_JWT_SECRET` 을 정하지 않으면 프로세스를 재시작할 때마다 새로
생성되어 기존 로그인 세션이 전부 만료된다.

### 3.2 마이그레이션

```bash
python -m alembic upgrade head
```

버전을 확인하지 않은 상태로 대시보드를 열면 없는 테이블을 조회한다.

## 4. 대시보드 해석

### 4.1 지원 프로필 (거버넌스 탭)

현재 설정이 지원하는 배포 조합과 위반 사항을 표시한다.

| 화면 상태 | 의미 |
|-|-|
| 위반 0건 | 지원 범위 안의 설정이다 |
| 위반 있음 | 위반 목록에 조치 방법이 표시된다. 그대로 배포하지 않는다 |

**위반 0건은 차단 기능이 검증되었다는 뜻이 아니다.** 계약 위반이 없다는 것은
설정 조합이 지원 범위 안이라는 사실만 말한다.

### 4.2 관측 범위 (거버넌스 탭)

경보가 없다는 말은 두 가지 상태를 구분하지 않는다. 실제로 아무 일도 없었는지,
아무것도 관측하지 못했는지 말이다. 이 화면이 그 구분을 제공한다.

| 상태 | 의미 | 조치 |
|-|-|-|
| 관측됨 | 이 기간의 수치는 비교 가능하다 | 정상 |
| 부분 관측 | 수치를 그대로 믿을 수 없다 | 큐 포화·카운터 리셋 항목 확인 |
| 관측 신호 없음 (stale) | 센서가 살아 있는지 확인되지 않는다 | 센서와 수집 프로세스 확인 |
| 알 수 없음 (unknown) | 무엇이 왜인지 판정할 수 없다 | 조치 생성 금지 |

**경보가 없다는 판단을 내리려면 먼저 관측 상태를 확인한다.** `stale` 이나
`unknown` 일 때의 경보 부재는 근거가 되지 않는다.

단계별 표에서 두 종류의 손실을 따로 본다.

| 항목 | 뜻 |
|-|-|
| 앱 drop | 애플리케이션이 버린 것. 입력 큐 포화, 알림 큐 포화 |
| 커널 drop | 커널 네트워크 스택이 버린 것. 애플리케이션 손실이 아니다 |

두 값은 합산하지 않는다. 원인과 분모가 다르다. 링크 구간(NIC·스위치) 손실은
이 도구에서 측정할 수 없으므로 `unknown` 으로 표시된다.

**관측된 트래픽이 0 이어도 장애로 판정하지 않는다.** 정상적인 구간일 수 있다.

### 4.3 위협 피드

| 상태 | 의미 |
|-|-|
| `ok` | 지표가 최신이다 |
| `stale` | 갱신이 늦었다. threat_intel 엔진은 최신 지표로 탐지하지 못한다 |

갱신 루프가 살아 있어도 모든 다운로드가 실패하면 `stale` 로 표시된다. 지표가
0건인 상태는 정상 상태와 구분되지 않으므로 상태값을 함께 본다.

## 5. 차단 정책 승인 절차

차단 정책은 세 단계로 나뉜다. 승인만 하고 적용하지 않은 상태가 정상적으로
남는다.

| 단계 | API | 역할 | 하는 일 |
|-|-|-|-|
| 1. 제안 | `POST /api/response-proposals` | analyst | 영향 범위를 계산해 제안만 남긴다 |
| 2. 승인 | `POST /api/change-proposals/{id}/approve` | admin | 대상·방향·TTL을 확정한다 |
| 3. 적용 | `POST /api/response-actions/{id}/activate` | admin | 방화벽에 반영을 시도한다 |

### 5.1 제안 단계에서 반드시 읽을 것

`GET /api/response-proposals/{id}/impact` 응답에는 두 범위가 분리되어 있다.

| 항목 | 뜻 |
|-|-|
| `observed_scope` | 확인된 자산 |
| `unconfirmed_scope` | 확인되지 않은 자산 |

`unconfirmed_scope` 는 무시할 수 없다. 공유 IP와 NAT 환경에서는 실제 업무
시스템이 그 안에 있을 수 있다.

**범위를 좁히지 못하면 제안이 만들어지지 않는다.** 넓은 IP 차단으로 대체하지
않는다. 좁히는 방법이 없는 것보다 넓게 막는 것이 위험하다.

### 5.2 적용이 거부되는 경우

| 사유 | HTTP | 확인 방법 |
|-|-|-|
| 승인된 대상·방향·TTL과 다름 | 409 | 승인 후 설정을 편집했을 때 발생한다. 재승인한다 |
| 승인 후 대상 매핑이 변경됨 | 409 | 승인 후 확인 시각이 지난 매핑. 매핑을 다시 확인한다 |
| 관측 상태가 stale 또는 unknown | 409 | 조치 생성 자체를 막는다 |
| 대상이 보호 대상 | 409 | 사설 대역·관리망·127.0.0.1 등 |
| TTL 이 상한 초과 또는 영구 | 422 | TTL 은 1~3600 초 |
| 동시 3개 또는 분당 1개 초과 | 429 | 속도 제한. 거절된 조치는 `requested` 상태로 남고 OS 는 건드리지 않는다 |

409 로 거절된 요청은 상한을 소모하지 않는다. 실행하지 않은 요청이 상한을 먹으면
실제로 적용할 수 있는 조치까지 막히기 때문이다. 상한은 **실행에 성공한 경로만**
차감한다.

### 5.3 적용 후 상태

| 상태 | 뜻 |
|-|-|
| `active_verified` | 방화벽에 반영되었고 조회로 확인했다 |
| `expired_verified` | 만료되었고 부재를 확인했다 |
| `removed_verified` | 수동 제거했고 부재를 확인했다 |
| `unknown` | 확인하지 못했다. 성공도 해제도 아니다 |
| `failed` | 적용이 실패했다 |

`unknown` 은 제거되지 않는다. 확인이 필요하면 `GET /api/response-actions/{id}`
로 영수증을 확인한다.

## 6. nftables 백엔드

방화벽 차단 백엔드는 두 가지다. `shadow` 는 아무것도 하지 않고 의도만
기록하며, `nftables` 는 실제 방화벽을 변경한다.

### 6.1 현재 상태

```
shadow    방화벽 접근 없음, 만료 미검증, 모드 shadow, 자동 차단 꺼짐
nftables  방화벽 접근 있음, 만료 미검증, 모드 shadow, 자동 차단 꺼짐
```

`nftables` 가 구현되어 있어도 만료가 검증되기 전에는 `shadow` 모드로 동작한다.
검증 전 적용을 시도하면 거부된다.

### 6.2 만료 검증

이 백엔드는 nftables 의 set 원소 timeout 기능으로 만료를 처리한다. 만료가
실제로 동작하는지는 문서가 아니라 장비에서 확인한다.

```bash
# 격리된 네트워크 네임스페이스에서 검증한다. 장비의 방화벽에 영향이 없다.
sudo python -m netwatcher.verify_nftables

# 실제 장비에서 검증한다. 이 도구가 소유한 inet nwwatcher 테이블만 사용한다.
sudo python -m netwatcher.verify_nftables --live
```

종료 코드 0 이면 검증 통과다. 통과 후에도 자동 차단은 꺼져 있다. 운영자가
명시적으로 켜야 한다.

검증이 다음 세 가지를 모두 확인한다.

1. 만료 시각 이전에 규칙이 존재한다
2. 만료 시각 이후에 규칙이 없다
3. 잔여 원소가 0 개다

세 번째 조건이 필요한 이유는 만료가 set 을 지우는 것이 아니라 **원소만
지우기 때문**이다. set 이 존재한다는 사실로 차단이 지속된다고 판단하면 안 된다.

### 6.3 안전 경계

| 규칙 | 내용 |
|-|-|
| 전용 테이블 | `inet nwwatcher` 만 사용한다 |
| 기존 방화벽 미접촉 | `ip filter` 테이블은 iptables-nft와 ufw가 관리한다. 건드리지 않는다 |
| 일괄 삭제 금지 | 비우기 명령과 다른 규칙 삭제가 없다 |
| 방향 제한 | `input` 만 지원한다 |
| 주소 범위 | IPv4 만 지원한다 |
| 셸 미사용 | 명령은 인자 배열로만 전달한다 |
| 보호 대상 제외 | 사설 대역·관리망·루프백·공유 주소는 자동 조치 대상이 아니다 |

## 7. 설정 비교와 리플레이

설정을 바꾸기 전에 같은 입력으로 기존 설정과 후보 설정을 비교한다.

```bash
curl -X POST localhost:38585/api/replay-runs \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"records": [...], "engines": ["port_scan"],
       "baseline_params": {"threshold": 20},
       "candidate_params": {"threshold": 40},
       "baseline_version": "v3.0", "candidate_version": "v3.1"}'
```

실행은 비동기다. `GET /api/replay-runs/{id}/diff` 로 결과를 받는다.

### 7.1 비교 결과 해석

`non_comparable_reasons` 가 비어 있지 않으면 **비교가 성립하지 않았다.**
결과 숫자를 읽기 전에 이 배열을 먼저 확인한다.

| 사유 코드 | 뜻 |
|-|-|
| `trace_incomplete` | 입력이 잘렸다 |
| `payload_engine_no_source` | 원본이 없어 재현할 수 없다 |
| `engine_not_supported` | 검증 범위 밖 엔진이다 |
| `version_scope_mismatch` | 버전 지문이 달라 차이의 출처를 특정할 수 없다 |
| `feature_not_recorded` | 필요한 특징값이 기록되지 않았다 |
| `evidence_expired` | 근거가 만료됐다 |
| `budget_exceeded` | 실행 예산을 초과했다 |

`rejected` 항목이 있으면 `removal_cause` 를 함께 본다. 재현 불가로 사라진
것과 조건 변경으로 줄어든 것은 다르다.

**관측이 사라진 것은 오탐이 줄었다는 증거가 아니다.** 정상 여부는 담당자
확인이다.

### 7.2 지원 엔진

| 엔진 | 재현하는 관측 |
|-|-|
| `arp_spoof` | 주소 바인딩 변화 |
| `port_scan` | 연결 시도 분포 |
| `data_exfil` | 전송량 초과 |

세 엔진은 관측 사실만 만든다. 악성 여부를 판정하지 않는다.

## 8. 장애 시 점검 순서

### 8.1 경보가 안 나올 때

1. 관측 범위 상태를 확인한다. `stale` 면 센서 문제다
2. `stale` 가 아니라면 백그라운드 서비스 상태를 확인한다
3. DB 저장이 안 되면 `db` 단계의 drop 카운터를 확인한다
4. 탐지 엔진이 꺼졌는지 설정을 확인한다

### 8.2 경보가 너무 많을 때

1. 속도 제한 설정(`alerts.rate_limit`)을 확인한다
2. 관측 범위의 `alert` 단계 억제 카운터를 확인한다
3. 화이트리스트를 확인한다
4. 설정 변경 이력을 확인한다. AI 가 설정은 바꾸지 않지만 제안은 남긴다

### 8.3 대시보드가 안 열릴 때

1. 기동 로그에서 지원 계약 위반으로 거부됐는지 확인한다
2. `web.host` 와 `auth.enabled` 조합을 확인한다
3. 포트 38585 의 사용 여부를 확인한다

## 9. 되돌리기

| 대상 | 방법 |
|-|-|
| 엔진 설정 변경 | 감사 로그에서 변경 이력을 확인해 이전 값으로 되돌린다 |
| 차단 조치 | `response_actions` 의 상태를 확인하고 수동 제거 경로를 사용한다 |
| 설정 제안 | 제안 이력에서 상태를 확인한다. 승인 전 제안은 아무것도 적용하지 않은 상태다 |
| alembic | `alembic downgrade` 를 사용한다. 데이터가 삭제될 수 있다 |

되돌리는 방법은 설정 파일이 아니라 기록에 있다. 승인·거절·적용·제거 결과는
각각 `config_proposals`, `response_actions`, `response_receipts` 에 남는다.
