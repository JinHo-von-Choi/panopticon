# 운영자 안내 — 이 도구가 무엇을 하고 무엇을 하지 않는가

작성일: 2026-10-06
대상: 이 도구를 설치하고 대시보드를 운영하는 사람

이 문서는 기능 사용법이 아니다. **이 도구가 보장하지 않는 것** 을 먼저
적었다. 보장하지 않는 것을 먼저 알아야 나중에 잘못된 확신을 갖지 않는다.

---

## 1. 지금 이 도구가 하는 일

- 지정한 인터페이스의 트래픽을 수집하고 탐지 엔진을 돌린다
- 탐지 결과를 PostgreSQL 에 저장하고 웹 대시보드로 보여준다
- 설정 변경은 사람이 승인해야 적용된다 (AI 는 제안만 올린다)
- 대시보드에서 "무엇을 관측했고 무엇을 관측하지 못했는지" 보여준다
- 예외 정책은 **제안** 형태로 만든다. 승인 없이는 아무 조치도 실행되지 않는다

## 2. 지금 이 도구가 하지 않는 일

이 목록이 기능 목록보다 중요하다.

| 하지 않는 것 | 이유 |
|-|-|
| 방화벽을 변경하지 않는다 | 검증된 만료 백엔드가 없다. `response.enabled` 는 꺼져 있다 |
| 경보가 없다고 해서 안전하다고 말하지 않는다 | 관측 범위 화면에서 "관측됨 / 부분 / 정체 / 알 수 없음" 을 구분해 준다 |
| 앵무새리를 감시하고 있다고 말하지 않는다 | 방화벽 차단이 아니라 관측 전용이다 |
| 두 버전을 비교해 "이게 좋아졌다"고 말하지 않는다 | 비교 불가 사유가 있으면 비교하지 않는다 |
| AI 가 승인하지 않는다 | AI 는 제안만 올린다. 승인은 사람이 한다 |
| 항상 켜져 있다고 말하지 않는다 | 정체된 위협 피드는 탐지 범위를 줄인다. 상태가 화면에 표시된다 |

## 3. 대시보드에서 반드시 확인할 세 가지

### 3.1 지원 프로필 (거버넌스 탭)

위반이 있으면 **배포하지 마세요.** 위반이 없다는 것은 "차단 기능이 검증되었다"
는 뜻이 **아닙니다.** 이 문구는 화면에 그대로 적혀 있다.

### 3.2 관측 범위 (거버넌스 탭)

| 표시 | 의미 | 해야 할 것 |
|-|-|-|
| 관측됨 | 이 창의 수치는 비교 가능 | 정상 |
| 부분 관측 | 수치를 그대로 믿지 마라 | 큐 포화·카운터 리셋 확인 |
| 관측 신호 없음 (stale) | 센서가 살아 있는지 확인되지 않음 | 센서 확인. **경보가 없다는 근거로 쓰지 마라** |
| 알 수 없음 (unknown) | 무엇이 왜인지 모름 | 확인 전 조치 금지 |

"관측된 트래픽이 0" 은 장애 선언이 아니다. 조용한 구간일 수 있다.

### 3.3 위협 피드

`stale` 이면 threat_intel 엔진은 최신 지표로 탐지하지 못한다. 갱신 루프가
살아 있어도 **모든 다운로드가 실패**하면 같은 상태가 된다.

## 4. 조치를 승인할 때 반드시 읽는 것

이 도구는 예외 정책을 **제안**한다. 제안 응답에는 반드시 다음이 들어 있다.

- `observed_scope` — **확인된** 영향 범위
- `unconfirmed_scope` — **확인되지 않은** 범위
- `uncertainty` — 왜 확인되지 않았는가
- `guardrails` — 이 제안을 자동으로 넓히지 않는다는 약속

`unconfirmed_scope` 를 무시하지 마라. 공유 IP·NAT·DHCP 환경에서는 그 안에
실제 업무 시스템이 있을 수 있다. **범위를 좁히지 못했으면 이 도구는
제안조차 만들지 않는다.** 넓은 IP 차단으로 대체하지 않는다. 대체하는
도구는 위험을 줄이는 것이 아니라 옮기는 것이다.

## 5. 자주 잘못 되는 해석

| 이렇게 읽음 | 실제로는 |
|-|-|
| "경보가 없으니 안전하다" | 센서가 살아 있는지부터 봐야 한다 |
| "계약 위반 없음이니까 차단이 된다" | 계약 통과와 enforcement 통과는 다르다 |
| "차단을 켰으니 막혔다" | `response.enabled` 는 꺼져 있다 |
| "경보가 줄었으니 오탐이 줄었다" | 정상 여부는 담당자 확인이다 |
| "비교가 됐다니 새 설정이 낫다" | 비교 불가 사유가 있으면 비교하지 않는다 |
| "적용됐다" | shadow 모드에서는 의도 기록일 뿐이다 |

## 6. 실패했을 때

- **DB 연결이 안 된다** — 이벤트가 저장되지 않는다. 관측 범위에서
  `db` 단계 `dropped_app` 이 쌓이는 것으로 보인다
- **큐가 찬다** — `input_queue` / `result_queue` 의 앱 drop 이 늘어난다.
  커널 drop 과 합산하지 않는다 — 원인이 다르다
- **카운터가 리셋된다** — 창이 끊긴다. 부분 관측으로 표시된다
- **설정 제안 큐가 막힌다** — 대기 큐의 사유를 확인한다. 기존 YAML 드리프트가
  사유일 수 있다 (경고로 표시되고 차단하지 않는다)

## 7. 감사와 되돌리기

- 승인·거절·적용 결과는 `config_proposals` 에 남는다
- 조치 생애주기(요청~만료 확인)는 `response_actions` + `response_receipts` 에 남는다
- 리플레이 실행과 비교 근거는 `replay_runs` / `replay_results` 에 남는다
- **되돌리려면 감사 로그를 뒤져야 한다.** 되돌리는 방법은 "설정" 에 있지 않고
  "기록" 에 있다
