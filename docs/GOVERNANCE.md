# 개발 거버넌스

이 저장소의 판정 규칙이다. 규칙을 어기면 게이트가 막거나 테스트가 실패한다.

## 1. 판정 규칙

### 1.1 꺼진 것과 고쳐진 것을 구분한다

기능을 끄면 경보가 멈추고, 경보가 멈추면 문제가 없어 보인다. 그래서 상태를
외부에서 확인할 수 있어야 한다.

- 지원 범위 밖의 조합은 기동을 거부한다 (`netwatcher/support.py`)
- 센서의 관측 상태를 외부에 노출한다 (`netwatcher/observability/observation.py`)
- 배포 가능 여부를 게이트가 판정한다 (`scripts/gates.py`)

### 1.2 계약을 통과한 것과 기능이 동작하는 것을 구분한다

지원 계약 통과는 설정 조합이 유효하다는 뜻이다. 차단이 동작한다는 증거가
아니다. 이 구분을 문서와 API 응답에 명시한다.

- 대시보드: 지원 프로필 화면에 "운영 검증을 통과했다는 뜻이 아니다" 를 표시
- API: `GET /api/response/capabilities` 의 `applies_to_os`, `kernel_expiry_verified`
- 로그: 지원 계약 강제 시 거부 사유를 남김

### 1.3 측정할 수 없는 값은 `unknown` 으로 남긴다

근거 없이 숫자를 만들지 않는다.

| 값 | 상태 |
|-|-|
| 앱 drop (같은 단계·같은 시간창의 분모) | 측정 가능 |
| 커널 drop (`/proc/net/softnet_stat`) | 측정 가능 |
| NIC·스위치 링크 손실 | `unknown` |
| SPAN 구성 완전성 | `unknown` |
| 원본이 없는 payload 엔진의 재현 | `unknown` |

**커널 drop 과 앱 drop 을 합산하지 않는다.** 분모와 원인이 다르므로 합계는
의미 없는 숫자가 되고, 애플리케이션 손실률로 오독된다.

### 1.4 손실률은 분모가 있을 때만 계산한다

분모(같은 단계·같은 시간창의 수신)가 없으면 백분율을 내지 않고 원시 계수와
`unknown` 을 반환한다.

### 1.5 확인하지 않은 것을 확인했다고 쓰지 않는다

| 상황 | 금지 | 규칙 |
|-|-|-|
| 방화벽 조회 실패 | 성공 또는 해제로 기록 | `unknown` |
| 근거 층 누락 | 값을 채워 넣음 | 누락 목록을 경보에 표시 |
| 비교 불가 | "줄어든 것" 으로 보고 | 비교 불가 사유를 함께 반환 |
| 정리 루프 | "차단 해제됨" | 만료 확인과 정리를 분리 기록 |
| OS 적용 명령 성공 | 적용 완료로 보고 | 조회로 재확인 |
| 실행 전에 거절된 요청 | 실행 시도로 집계 | 상한과 이력 모두에서 제외 |

### 1.6 판단은 재현되어야 한다

판정 결과가 개인 환경에 따라 달라지면 판정이 아니다. 게이트는 `.env` 를
읽지 않는다 (`NETWATCHER_SKIP_DOTENV`).

### 1.7 승인하지 않은 것은 반영하지 않는다

| 행위 | 최소 역할 |
|-|-|
| 조회 | viewer |
| 제안 접수, 리플레이 실행, 엔진 설정 조회 | analyst |
| 엔진 설정 쓰기, 제안 승인, 조치 승인·적용 | admin |

엔진 설정 쓰기는 대시보드에서 직접 편집하는 경로이므로 ADMIN 이 필요하다.
승인 또한 설정 쓰기와 같은 역할을 요구한다.

### 1.8 AI 는 판단하지 않는다

AI 가 할 수 있는 것: 탐지 결과 설명, 오탐 후보 제안.
AI 가 할 수 없는 것: 승인, 대상 범위 결정, TTL 결정, 방화벽 변경.

게이트 G0-2 가 AI 경로에서 설정 쓰기·런타임 변경·방화벽 호출이 없음을
정적으로 확인한다.

### 1.9 좁힐 수 없으면 좁히는 대안을 만들지 않는다

범위를 좁히지 못하는 상황에서 넓은 차단으로 대체하지 않는다. 제안 자체를
만들지 않는다.

### 1.10 권한 경로는 좁게 유지한다

외부에서 들어온 값이 방화벽까지 도달하는 경로는 대상·방향·TTL 세 값뿐이다.
그 외의 값은 실행기로 전달되지 않는다. 명령은 인자 배열로만 실행하고 셸을
사용하지 않는다. 게이트 G0-12 가 생성되는 명령을 직접 검사한다.

## 2. 게이트

`python scripts/gates.py` — 13개 게이트. 게이트는 설정이 올바른지 검사하지
않는다. **이 상태로 배포해도 되는지** 판정한다. 통과로 오인될 수 있는 항목을
검사 목록에 넣지 않는다.

```
python scripts/gates.py                    # 전체
python scripts/gates.py --gate G0-12       # 하나
python scripts/gates.py --json             # CI용
```

### 2.1 검사 성격이 다른 게이트

| 게이트 | 성격 |
|-|-|
| G0-1 ~ G0-10 | 계약 위반을 막는다 |
| G0-11 | 리플레이가 운영 경로에 닿지 않는지 확인한다 |
| G0-12 | 강제 적용 가능성을 잘못 표시하지 않는지 확인한다 |
| G0-13 | 마이그레이션과 스키마 정의가 일치하는지 확인한다 |

G0-11, G0-12, G0-13 은 **기능이 없는 것을 확인하는 게이트** 다. 기능이 없는
것도 배포 판단의 일부이기 때문이다.

### 2.2 게이트 추가 기준

게이트는 다음 조건을 모두 만족해야 한다.

1. 위반을 실제로 심었을 때 FAIL 이 난다
2. 복원하면 PASS 가 난다
3. 출처 문자열이 아니라 **출력·동작** 을 검사한다

세 번째 조건이 없다면 주석을 위반으로 오인하는 오탐이 생긴다.

### 2.3 게이트와 테스트의 관계

| 대상 | 담당 |
|-|-|
| 게이트 | 정적 검사. 소스·설정·생성 명령 |
| 단위 테스트 | 순수 함수와 경계값 |
| 통합 테스트 | 실제 DB, 실제 엔진, 실제 디스패처 |
| 노예 | 실제 경로 종단간. 모킹을 쓰지 않는다 |

실제 DB 를 쓰는 라우터 테스트는 `TestClient` 대신 같은 이벤트 루프의
`httpx.ASGITransport` 를 쓴다. `TestClient` 은 앱을 별도 루프에서 실행해
asyncpg 커넥션이 끊긴다.

## 3. 스키마 변경

테스트 데이터베이스는 마이그레이션이 아니라 `netwatcher/storage/schemas.py`
의 `ALL_SCHEMAS` 로 만들어진다.

```
1. alembic/versions/NNN_*.py 작성
2. schemas.py 에 같은 CREATE TABLE 과 인덱스 추가
3. ALL_SCHEMAS 목록에 추가
4. alembic upgrade head
5. python scripts/gates.py --gate G0-13
```

2번 또는 3번을 빠뜨리면 테스트는 통과하지만 해당 테이블이 없다. G0-13 은 이
불일치를 검사한다.

## 4. 마이그레이션 규칙

- down_revision 은 직전 리비전과 연결한다
- downgrade 를 함께 작성한다
- 일시적 작업 테이블은 `upgrade()` 안에서 생성하고 같은 함수에서 제거한다
- 파티셔닝 전 테이블처럼 마이그레이션이 끝나면 사라지는 테이블을
  `ALL_SCHEMAS` 에 넣지 않는다

## 5. 대시보드 변경

- 사용자 입력은 `esc()` 로 이스케이프한다. 속성값은 `escAttr()`
- 인라인 이벤트 핸들러에 템플릿 값을 넣지 않는다
- 렌더 함수는 실제 페이로드로 Node 에서 실행해 출력 문자열을 검사한다
- 토스트 심각도는 스타일시트에 정의된 값만 쓴다

## 6. 변경 전 점검

- [ ] 판정 로직을 추가하면 근거가 없을 때 무엇을 반환하는지 정했는가
- [ ] 상태를 추가하면 그 상태의 이유가 함께 반환되는가
- [ ] 판단 기준을 추가하면 게이트로 확인되는가
- [ ] 게이트를 추가하면 위반을 심어 FAIL 을 확인했는가
- [ ] 배선을 추가하면 계측값이 실제로 채워지는지 확인했는가
- [ ] 주석이 아니라 검사로 강제할 수 있는 규칙인가
- [ ] 실패 경로가 조용히 성공처럼 보이지 않는가
