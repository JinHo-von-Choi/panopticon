# 합성 성능 시험

EVE 수집과 패킷 탐지 성능은 도구를 나누어 측정합니다. 두 도구 모두 별도 로컬 PostgreSQL DB에 임시 스키마를 구성했다가 작업 종료 즉시 지웁니다. 이때 DB 이름은 반드시 `netwatcher_perf_`로 시작해야 합니다. DB 비밀번호는 `NETWATCHER_PERF_DB_PASSWORD` 환경변수로 넘겨주고, 출력 경로에는 소스 저장소 바깥에 위치한 새 디렉터리를 지정해야 합니다.

## EVE 수집

`scripts/perf_eve.py`는 합성 Suricata 경보를 파일에 쓴 뒤 Panopticon이 이를 읽어 DB에 적재하기까지 걸리는 전 과정을 측정합니다.

```bash
NETWATCHER_SKIP_DOTENV=1 .venv/bin/python scripts/perf_eve.py \
  --duration-seconds 30 --events-per-second 1000 \
  --db-name netwatcher_perf_local --db-user netwatcher \
  --output-dir /tmp/panopticon-eve-perf-run
```

실행 후 `result.json` 파일의 `emitted_records`, `stored_records`, `stored_events`, `all_emitted_records_stored`, `source_duration_completed` 항목을 직접 확인해야 합니다. 설정한 요청 속도와 실제 생성 속도 사이에는 간극이 생길 수 있습니다. 이벤트 생성이 끝난 뒤에도 큐에 남은 입력을 비우기 위해 최대 30초 동안 추가 처리를 이어갑니다. 수집 작업을 종료하고 진행 중이던 저장을 마무리한 다음, 동일한 DB 조회 시점에서 기록 수와 사건 수를 함께 집계합니다. 수집 상태는 종료 직전에 기록하므로 시험 종료 자체를 수집 장애로 잡지 않습니다. DB에 들어가지 못한 입력 수치를 실제 NIC의 패킷 손실률로 곧장 치환해 계산해서는 안 됩니다.

지연 시간은 원본 경보 생성 시각부터 DB 저장이 완료된 시점까지를 잽니다. p95는 전체 관측값을 고정 크기 히스토그램으로 묶은 상한값이며 구간 폭은 10%입니다. 시스템 시계에 오류가 있으면 측정된 지연 수치는 신뢰하기 어렵습니다. 기록되는 CPU 시간에는 이벤트 생성기와 성능 측정 코드 실행 시간이 모두 들어가며, 최대 RSS는 프로세스 구동 이후 찍힌 최고치입니다. 반면 별도 프로세스로 뜨는 HTTP 서버, Suricata, DB의 자원 사용량은 이 측정치에서 빠집니다.

기본 입력 파일과 저장 용량 상한은 각각 256MiB, 보관 레코드 수는 250,000개로 묶여 있습니다. 긴 시험을 돌릴 때는 `--max-source-bytes`, `--max-retained-bytes`, `--max-retained-records` 옵션으로 워크로드에 알맞은 한도를 직접 지정해야 합니다. 보관 한도를 넘기면 전체 입력을 담아내지 못합니다. 정상 종료 판정은 요청한 입력 생성 시간을 채우고, 입력 용량 상한에 도달하지 않으며, 생성된 모든 입력이 DB에 온전히 저장되고 수집 상태가 정상일 때만 내려집니다. 도중에 오류로 입력 생성이 일찍 멈추면 생성분을 전부 저장했더라도 시험은 실패로 처리됩니다.

이 시험은 현재 소스 트리의 테이블 스키마 정의를 그대로 씁니다. 실제 운영 배포용 마이그레이션 호환성이나 실망 네트워크 처리량, 장시간 안정성 같은 지표는 별도 테스트 파이프라인에서 직접 검증해야 합니다.

## 패킷 탐지

`scripts/perf_replay.py`는 합성 패킷을 흘려보내 탐지 엔진, 경보 저장, 증거 수집 로직의 부하를 검증하는 로컬 개발용 측정 도구입니다. 임시 스키마는 별도 PostgreSQL DB 안에 생성되고 측정이 끝나면 즉시 지워집니다. 운영 DB나 실제 네트워크 장비는 건드리지 않습니다.

## 실행

DB 이름은 `netwatcher_perf_`로 시작해야 하고 로컬 DB만 쓸 수 있습니다. 비밀번호는 `NETWATCHER_PERF_DB_PASSWORD` 환경변수에 설정합니다. 출력 경로에는 소스 저장소 밖의 새 디렉터리를 지정합니다.

```bash
NETWATCHER_SKIP_DOTENV=1 .venv/bin/python scripts/perf_replay.py \
  --scenario normal --duration-seconds 30 --pps 100 --pcap \
  --db-name netwatcher_perf_local --db-user netwatcher \
  --output-dir /tmp/panopticon-perf-run
```

| 시나리오 | 측정 대상 |
| --- | --- |
| `normal` | 합성 DNS·TCP 입력의 기본 처리 |
| `mixed` | 기본 입력과 SYN 스캔의 탐지 경로 |
| `alert-storm` | 같은 조건의 경보 집계와 저장 |
| `unique-key` | 다른 조건의 경보가 증가할 때의 저장 부하 |

`--pcap` 옵션을 주면 증거 패킷 파일도 함께 씁니다. `--alerts-per-second`는 경보 직접 주입 시나리오가 목표로 삼는 처리 속도입니다. 이미 존재하는 출력 디렉터리는 덮어쓰지 않습니다.

## 결과 해석

`result.json`을 볼 때는 요청 입력량과 실제 생성량, 처리·저장량, 큐 대기 시간과 누락 수치, CPU 및 메모리 점유율을 종합해 대조해야 합니다. 생성기 병목으로 애초에 내보내지 못한 입력은 애플리케이션의 패킷 유실과 명확히 구분해야 합니다. 큐 내부 패킷 바이트 집계에는 Python 런타임의 객체 메모리 오버헤드가 잡히지 않습니다.

조건을 비교할 때는 반드시 동일한 시드, 입력량, 기간을 둔 채 변수를 하나씩만 바꿔가며 측정해야 합니다. 탐지 사건 수가 줄었다고 해서 오탐률이 낮아졌다고 단정해서는 안 됩니다. 공격과 정상 트래픽 레이블이 사전에 검증된 별도 테스트 샘플을 갖춰야만 정확한 판단이 가능합니다.

이 도구는 단일 워커 프로세스로만 돕니다. 실제 NIC의 물리적 한계, 외부 알림 시스템 연동, 통계 집계 저장, 네트워크 차단 성능까지는 다루지 못합니다. 측정된 CPU·메모리에는 프레임워크 초기화와 프로세스 종료 오버헤드가 섞여 있으며, DB 프로세스 자체의 리소스 소모량은 별도 집계 대상입니다. 물리 장비의 실질 처리량, 디스크 I/O 지연, 장기 연속 구동 안정성은 타깃 환경에서 따로 계측해야 합니다.
