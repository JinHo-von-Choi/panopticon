# 2026-10-08 반복 폭풍과 이벤트 루프 양보 재현

격리 PostgreSQL 16·합성 입력·PCAP on·workers=1에서 10초간 반복 경보 10,000건을
주입했다. 운영 DB·NIC·방화벽·외부 채널을 사용하지 않았다. DB 컨테이너는
네트워크 없이 CPU 1코어/RAM 256MiB이며 앱의 CPU 제한과 전용 하드웨어는 없다.

시간 분할은 패킷 한 건을 중단하지 않는다. 최대 500개를 연속 처리하던 버퍼가
10ms 이후 다음 패킷부터 제어를 양보해 타이머·주입·저장 태스크가 실행될 기회를
얻는다. 이후 실행에서는 모든 주입 경보가 집계됐고 결과 큐 app drop은 없었다.

두 실행 모두 요청 1,000pps를 생성하지 못했다. CPU·생성 패킷·전체 이벤트 수의
차이는 동일 실입력 비교가 아니며 처리량 개선율로 해석하지 않는다. 30분/10분
부하, 지연 p99, HDD I/O 감소, 커널/링크 손실 목표는 아직 미검증이다.

두 보고서의 revision은 e83cae0이다. 후자는 그 revision 위의 capture 시간 분할
변경이 포함된 dirty 작업 트리였고, 기존 사용자 .gitignore 변경도 있었다.

### 후속 프로파일과 공통 파싱 실험

격리 PostgreSQL·합성 mixed 입력·PCAP 사용·단일 워커에서 cProfile을 켜고
30초/요청 1,000pps를 실행했다. 30,000건 계획 중 9,420건을 생성했고 drain 포함
38.13초, CPU 39.40초, peak RSS 556,437,504 bytes였다. snapshot 시 처리 전 입력은
3,685건이었다. 프로파일 비용과 소스 생성 부족, 미처리 입력을 포함하므로 이를
1,000pps·무손실·메모리 목표 통과로 해석하지 않는다. NIC/HDD/외부 채널/통계 flush
측정이 아니며 원문은 `/tmp/panopticon-perf-profile-main-20261008/`에 있다.

Scapy getlayer/haslayer 반복 호출이 내부 CPU 시간 상위에 나타났다. 주소 공통
함수의 존재 확인 후 다시 추출하는 탐색을 한 번의 getlayer로 줄였다. IPv4/IPv6/
ARP/비-IP/중첩 IP/HTTP-DNS 입력 6종의 기존 출력과 비교한 후, 번갈아 5회씩
6,000호출을 측정한 중앙값은 92.60ms→74.67ms(약 19.4% 감소)였다. 이는 미리
구성한 패킷의 주소 추출 함수 측정이며 전체 파이프라인 개선율이 아니다.
packet_info의 같은 변경은 약 2.1%, OS hint는 약 3.2% 악화로 이득이 불명확해
적용하지 않았다. 무측정 대규모 캡처 재작성이나 워커 기본 증설은 하지 않았다.
원문은 `/tmp/panopticon-layer-benchmark.json`이며 재현 가능한 프로토콜 출력과
변경된 패킷 주소의 신선도를 회귀 시험으로 확인한다.


### 콘솔의 목록 상한과 렌더 비교

실제 API·Chrome headless의 현재 화면에서 합성 live 사건 1,000건 후 200행 상한을
확인했다. 같은 현재 DOM·합성 입력에서 이전 revision 74209a1의 console.css·
renderEventRow·날짜 유틸리티와 현재 코드를 번갈아 10회 200행 생성+layout한

편차와 방향 변화가 있어 일관된 속도 향상으로 표시하지 않는다. 이전 제품 전체·
장시간·낮은 사양 단말의 성능을 대신하지 않는다. 비교 원문과 9개 탭/2개 상세
패널의 일반 텍스트 대비 검사 범위는
